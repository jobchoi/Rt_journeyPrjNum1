# 추후 확장 결정안

사용자 결정 전 검토용 제안이다. 이번 작업에서는 아래 기능을 구현하거나 회계·권한·보존 정책을 확정하지 않는다. 현재 일반 원장 수정·버전 충돌 방어·변경 이력은 유지하며, 결산은 계산 보고서다.

## 1. 거래 취소 및 장학 지급 연계 정정

하려는 일: 잘못 등록한 거래와 실제 반환·환급을 구분하고, 지급 기록과 원장이 어긋나지 않게 정정 근거를 보존한다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| 원거래에 취소 상태를 부여하고 집계에서 제외 | 오입력 취소가 단순함 | 과거 보고서가 달라지며 이미 마감한 기간 처리 기준 필요 |
| 원거래를 보존하고 연결된 반대 거래와 정정 거래를 추가 | 취소·정정 경로와 금액을 추적하기 쉬움 | 실적·이자·이월금 집계에서 반대 거래 처리 규칙 필요 |
| 기간 내 오입력은 상태 취소, 마감 후와 실제 반환은 연결 거래 | 상황별 회계 표현 가능 | 사용자 흐름과 검증 규칙이 복잡함 |

권장안: 연결된 반대 거래·정정 거래 방식. 취소 사유·처리자·원거래 연결을 남기고 장학 지급 상태와 원장 변경을 같은 트랜잭션으로 반영한다. 중복 취소와 동시 요청을 차단하고, 실제 송금 취소와 장부 정정을 화면에서 구분한다. 마감 이후 귀속일은 사용자 결정에 따른다.

사용자가 답해야 할 질문:
- 오입력 취소와 실제 반환을 어떤 날짜·분류로 집계하며 총 입출금 실적에 포함할 것인가?
- 장학 지급 정정 시 지급 상태·선발 금액도 바꾸는가? 외부 송금 확인은 누가 하는가?
- 취소·정정 권한과 별도 승인자는 누구인가? 기존 일반 수정 권한도 제한할 것인가?
- 마감 기간의 취소를 허용하는가, 다음 열린 기간에 반영하는가?

## 2. 증빙 첨부, 계좌별 원장, 동명이인 식별

하려는 일: 거래의 증빙과 소속 계좌·거래 상대를 명확히 연결하면서 개인정보 노출과 중복 집계를 줄인다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| 기존 자유 입력에 증빙 경로·계좌 이름·식별 메모만 추가 | 도입이 빠름 | 이름 변경·동명이인·권한 관리가 불안정함 |
| 계좌·거래처에 내부 ID 부여, 증빙은 접근 통제된 저장소에 보관 | 안정적인 연결과 계좌별 집계·접근 제어 가능 | 데이터 이관과 파일 보안·백업 정책 필요 |
| 외부 문서 저장소와 거래처 시스템 연동 | 기존 조직 관리 체계 활용 가능 | 외부 권한·장애·계약 및 연동 비용에 의존함 |

권장안: 내부 계좌·거래처 ID와 접근 통제된 증빙 저장. 과거 미지정 거래는 임의로 배정하지 않고 미지정 그룹으로 유지한다. 동명이인은 별도 ID로 구분하고 이름만으로 병합하지 않는다. 계좌 간 이체는 연결된 두 거래로 표현하되 통합 실적에서 중복 포함하지 않는 규칙을 먼저 결정한다. 증빙은 허용 형식·크기 검증 및 인증된 다운로드를 적용하는 방향을 제안한다.

사용자가 답해야 할 질문:
- 관리할 계좌·현금함·기금은 무엇이며 계좌별 기초 잔액과 내부 이체는 어떻게 처리하는가?
- 거래처 식별에 필요한 최소 정보는 무엇인가? 동명이인 구분용 내부 코드로 충분한가?
- 증빙 열람·추가·교체·삭제 권한은 누구에게 주며 교체 이력을 보존하는가?
- 증빙·거래처·백업의 보존 기간과 삭제·익명화 기준은 무엇인가?

## 3. 결산 확정, 마감 잠금과 승인

하려는 일: 특정 기간의 결산 근거를 고정하고 확정 후 등록·수정·가져오기·취소로 보고서가 바뀌는 것을 통제한다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| 확정 시 보고서 스냅샷만 저장 | 도입이 쉽고 당시 수치 재현 가능 | 이후 원장과 확정 보고서가 달라질 수 있음 |
| 기간 잠금과 담당자 직접 확정 | 모든 쓰기 경로의 일관된 통제 가능 | 작성자 스스로 승인할 수 있고 재개방 관리 필요 |
| 작성·검토·승인 분리, 기간 잠금과 스냅샷 보존 | 책임 분리와 감사 추적에 유리함 | 승인 인력과 반려·재개방 흐름 필요 |

권장안: 작성·승인 분리와 기간 잠금, 확정 보고서 버전 보존. 확정은 이월 거래를 자동 생성하지 않는다. 잠금 확인은 수동 입력·수정·은행/CSV 가져오기·취소에 공통 적용하고, 검증과 쓰기를 원자적으로 처리하는 설계가 필요하다. 재개방은 권한·사유·이력을 남기고 재확정 버전을 추가한다.

사용자가 답해야 할 질문:
- 월별·연별 중 어떤 단위로 마감하며 회계연도와 시간대는 무엇인가?
- 작성자와 승인자를 분리할 수 있는가? 역할별 승인 권한과 대결 기준은 무엇인가?
- 확정 후 소급 수정·재개방을 허용하는가? 이전 보고서는 누가 얼마 동안 조회하는가?
- 미분류·중복 후보·증빙 누락·은행 잔액 불일치 중 어떤 항목이 확정을 막는가?

## 4. 운영 인증 쿠키 정책, 배포·복구·모니터링

하려는 일: 인증 세션 보호와 반복 가능한 배포·복원을 마련하고 장애를 민감 정보 없이 감지한다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| 단일 서버·SQLite 유지, HTTPS 프록시와 정기 백업 운영 | 현재 구조를 유지하고 운영 부담이 작음 | 단일 장애 지점과 복구 대기 시간 존재 |
| 관리형 앱·DB·파일 저장소로 이전 | 백업·가용성 운영을 서비스에 위임 가능 | 비용·데이터 이전·의존성 및 배포 설계 변경 필요 |
| 자체 다중 서버·DB 운영 | 인프라 통제와 확장성 확보 | 운영 인력·동시성·백업 관리 부담이 큼 |

권장안: 현재 규모에서는 단일 서버를 유지하며 HTTPS, 운영 쿠키 정책, 검증된 백업·복원 절차부터 정한다. 운영 쿠키는 Secure·HttpOnly와 서비스 도메인/로그인 흐름에 맞는 SameSite·만료·로그아웃 정책을 설계하고 쿠키 인증 쓰기 요청에는 CSRF 방어를 포함한다. 비밀키는 코드 밖에서 관리한다. 배포 전 마이그레이션 백업과 복원 시험을 수행하며 코드 롤백과 DB 복원을 별도로 정의한다. SQLite 일관성 백업과 증빙 파일의 복원 시점을 맞추고 백업을 별도 위치에 보관한다. 상태 확인·오류율·디스크·백업 실패를 감시하되 토큰·원장·개인정보 원문을 로그에 넣지 않는다.

사용자가 답해야 할 질문:
- 운영 도메인·HTTPS 종료 위치·외부 로그인 또는 교차 사이트 이용이 있는가?
- 세션 유지 시간, 공용 PC 사용, 강제 로그아웃·키 교체 요구는 무엇인가?
- 허용 데이터 손실 시간(RPO), 복구 시간(RTO), 배포 중단 허용 시간은 얼마인가?
- 백업 위치·암호화·보존 기간·복원 시험 주기와 담당자는 누구인가?
- 장애 알림 수신자·연락 경로·대응 시간, 로그 보존 기간과 운영 접근 권한은 무엇인가?
