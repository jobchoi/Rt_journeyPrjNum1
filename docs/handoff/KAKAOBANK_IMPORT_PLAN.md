# 카카오뱅크 거래내역 가져오기 계획

작성일: 2026-11-20. 구현 전 검토 문서이며 실제 거래 데이터는 포함하지 않는다.

## 현재 상태

- FastAPI, SQLAlchemy, SQLite, Jinja2 기반 기금 원장: 수동 입출금, 검색·결산·보고서/CSV·인쇄, 수정 이력과 발표 대시보드가 구현되어 있다. 기존 장학 기능은 보존된다.
- CSV 가져오기는 재정 권한 사용자만 `POST /api/finance/transactions/import`를 이용한다. UTF-8 BOM 허용, 최대 5MB, `transaction_date`, `transaction_type`, `amount`, `description`, `external_reference` 필수, `counterparty`, `category` 선택이다. 날짜는 ISO 형식, 방향은 income/expense, 금액은 양의 정수다.
- 거래번호는 파일 내 유일하고 DB 전체에서 유일해야 한다. 한 행이라도 오류 또는 기존 중복이면 전체 저장을 거부하며 동시 저장 충돌도 409로 처리한다. 수동 입력의 자동 생성 번호는 은행 거래와 연결되지 않는다. 현재 파일별 미리보기·중복 건너뛰기는 없다.
- 실행: `python -m pip install -r requirements.txt`, `python scripts/upgrade_finance.py`, `python scripts/create_superuser.py --email admin@example.com --name "기금 관리자"`, `JWT_SECRET_KEY` 설정 후 `python -m uvicorn src.main:app --reload --host 127.0.0.1 --port 8001`. 업그레이드는 DB 백업과 변경을 수행하므로 운영 환경에서는 별도 판단이 필요하다. 대안으로 `./manage.sh start` 및 `./manage.sh status`. 검증 명령은 `python -m pytest -q`, `git diff --check`다. 이번 분석에서 테스트는 실행하지 않았다.
- `TASKS.md` 미완료: 거래 취소·장학 지급 연계 정정, 증빙·계좌별 원장·동명이인 식별, 결산 확정/마감 잠금·승인, 운영 인증 쿠키·배포·복구·모니터링.
- 분석 당시 `develop`은 `origin/develop`과 표시상 동일한 `7448338`이며 작업 트리는 깨끗했다. 원격 서버 조회 없이 로컬 추적 정보만 확인했다.

권장안은 사용자가 공식 앱에서 엑셀을 내려받아 업로드하고 미리보기와 확인 후 반영하는 방식이다. 은행 인증정보를 보관하지 않고 현 CSV 원장 흐름을 활용할 수 있다. 앱 메뉴와 실제 파일 특성은 샘플로 검증해야 하며 완전 자동화는 아니다. PDF는 엑셀이 불가능할 때만 정확도 검증 후 고려한다.

## 연결 설계 초안

1. 권한 있는 사용자가 파일을 업로드한다. 확장자·실제 형식·크기·행 수를 제한하고 암호화/손상 파일, 수식·매크로 등 예상 밖 형식을 안전하게 거부한다. 원본을 로그나 저장소에 남기지 않고 임시 파일은 성공·실패 시 삭제한다. 파일명에도 개인정보가 있을 수 있으므로 기존 `source_filename`에는 안전한 고정 이름만 사용한다. 전송 및 접근 보호, 백업·보존기간은 배포 환경에서 정한다.
2. 확인된 파일 형식별 파서가 날짜/시각, 입출금, 양의 원 단위 금액, 상대방과 적요를 공통 행으로 변환한다. 빈 값, 금액·날짜·방향, 잘못된 분류를 검증하고 불확실한 매핑은 사람이 수정한다. 일반 분류를 기본으로 하되 이자·장학금 등은 근거 없이 확정하지 않는다. 잔액을 이월금이나 거래로 자동 생성하지 않는다.
3. 미리보기에서 신규·중복 후보·오류와 합계를 보여주고 사용자 확인을 받는다. 은행의 안정적인 거래 고유번호가 존재하고 기간 변경에도 유지되는지 확인되면 계좌별 내부 식별자와 출처를 포함한 결정적 `external_reference`를 사용한다. 실제 계좌번호를 키나 로그에 넣지 않는다. 길이 제한 및 기존 전역 유일 제약과 충돌 가능성을 검토한다.
4. 고유번호가 없다면 날짜/시각·방향·금액 등으로 만든 지문은 동일한 합법적 거래를 구분하지 못하고 내보내기 순서도 변할 수 있다. 자동 중복 판정이나 임의 순번에 의존하지 말고 모호한 후보는 사용자 대조·선택으로 처리하며, 동일 파일과 기간 겹침의 재처리 규칙을 샘플로 확정한다. 기존 수동 거래는 자동으로 동일 거래라고 단정하지 않고 후보로 제시한다.
5. 확인된 행을 기존 CSV 계약에 맞춰 변환하고 공통 검증·저장 서비스를 추출해 재사용하는 방안을 구현 시 검토한다. 현재 API는 중복 하나로 전체 거부하므로 신규만 가져오기 기능을 제공하려면 서버에서 중복 재검사와 원자적 저장을 설계해야 한다. 동시 요청은 DB 유일 제약으로 최종 방어하고 충돌 시 재미리보기를 요구한다. 기존 CSV 동작은 유지한다. 계좌별 원장이 아직 없으므로 다중 계좌는 별도 설계·마이그레이션이 필요하다.

## 필요한 샘플과 확인 사항

개인정보를 가린 실제 내보내기 형식의 **합성 또는 비식별 샘플**을 요청한다. 파일 자체에 이름, 계좌번호, 이메일, 거래처, 메모, 잔액 등 민감정보가 남지 않게 하고 비밀번호·인증정보는 절대 포함하지 않는다. 열 이름·시트 구조·날짜/금액 형식은 유지하고 값은 가상값으로 대체한다. 입금·출금·이자, 같은 시각과 금액의 별도 거래, 기간이 겹치는 두 파일, 빈 값·긴 메모가 있으면 좋다. 거래 고유번호가 있다면 가상값으로 바꾸되 겹친 파일 사이의 동일성은 유지한다. PDF가 필요한 경우 텍스트형/스캔형 여부를 확인할 비식별 샘플도 요청한다. 계좌 유형, 원하는 가져오기 주기, 기존 수동 거래와의 대조 방식도 확인한다.
